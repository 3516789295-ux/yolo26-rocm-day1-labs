**中文** · [跳到英文](#english)

感谢参与本课程仓库!这里是学生与讲师共同维护的实训项目。我们欢迎:翻译改进、文档澄清、bug 修复、新的教学实验想法。

## 提交 PR 的流程

1. **Fork + 分支**:从 `main` 拉出 `feat/你的主题` 或 `fix/你的主题` 分支。
2. **本地验证**(必须全部通过):
   ```powershell
   .\.venv\Scripts\python.exe -m pytest -q          # 16 项回归全过
   .\.venv\Scripts\python.exe -m pip check          # 无依赖冲突,三件套版本未漂移
   ```
   如果改动了 Notebook 或 `build_notebooks.py`:
   ```powershell
   .\.venv\Scripts\python.exe build_notebooks.py    # 重新生成(单一事实源)
   ```
   Notebook 由 `build_notebooks.py` 生成——请修改生成器,不要手改 `.ipynb`;Markdown cell 保持中英对照。
3. **诚信红线**(PR 检查项):
   - 不得删除/绕过 ROCm 门禁(`require_rocm`)、数据泄漏检测、A/B 纯度断言;
   - 不得预置任何"性能/精度提升"结论或伪造训练产物;
   - 训练产物(`*.pt`)与数据集不入库(已被 `.gitignore` 排除)。
4. **提交 PR**:填写 PR 模板(现象/根因/验证证据),关联相关 Issue。

## 好的 PR 示例

- 修正某段英文翻译的术语错误(小而清晰);
- 为 `course/lab_utils.py` 增加一项新的标签 QA 检查 + 对应测试;
- 在 `docs/TROUBLESHOOTING` 增加你踩到的新坑及解法;
- 用新的单变量(如 batch、lr)扩展 Lab E 的实验脚本(**先开 Issue 讨论**)。

## 报告问题

提 Issue 时请附:操作系统与 GPU 型号、`reports/environment.json`、完整报错栈、复现步骤。
敏感信息(代理地址、令牌)请先脱敏。

# Contributing Guide (English)

Thanks for contributing! This repository is maintained by students and instructors together. We welcome: translation improvements, documentation clarifications, bug fixes, and new teaching-experiment ideas.

## PR workflow

1. **Fork + branch**: branch off `main` as `feat/<topic>` or `fix/<topic>`.
2. **Verify locally** (all must pass):
   ```powershell
   .\.venv\Scripts\python.exe -m pytest -q          # all 16 regressions pass
   .\.venv\Scripts\python.exe -m pip check          # no conflicts; the torch trio did not drift
   ```
   If you touched notebooks or `build_notebooks.py`:
   ```powershell
   .\.venv\Scripts\python.exe build_notebooks.py    # regenerate (single source of truth)
   ```
   Notebooks are generated by `build_notebooks.py` — edit the generator, never the `.ipynb` files; keep markdown cells bilingual.
3. **Integrity red lines** (PR checklist):
   - Never remove or bypass the ROCm gate (`require_rocm`), the data-leak checks, or the A/B purity assertions;
   - Never pre-bake any "performance/accuracy improvement" conclusion or fabricate training artifacts;
   - Training artifacts (`*.pt`) and datasets stay out of the repo (already excluded by `.gitignore`).
4. **Open the PR**: fill in the PR template (symptom / root cause / verification evidence) and link the issue.

## Examples of good PRs

- Fixing a terminology mistake in an English translation (small and clear);
- Adding one new label-QA check to `course/lab_utils.py` together with its test;
- Documenting a new pitfall and its fix in `docs/TROUBLESHOOTING`;
- Extending Lab E with a new single variable (e.g. batch, lr) — **open an issue to discuss first**.

## Reporting issues

When filing an issue, include: OS and GPU model, `reports/environment.json`, the full traceback, and reproduction steps. Scrub sensitive values (proxies, tokens) first.
